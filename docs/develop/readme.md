# 把一份模板发给 AI，让它交付一整套软件

**这不是代码库，也不是安装包工具。**

它是 **六份写给 AI 的开发指令模板**。你选一条技术路线，把整份模板发给 AI，然后用自然语言说需求。AI 按固定的需求协议和十二层工程标准，交付一套能构建、能测试、能打包、能部署的完整工程。

[选一条路线](#六条技术路线) · [三步开始](#三步开始) · [常见问题](#常见问题) · [开发者文档](docs/readme.md)

> 不是让 AI“多写点代码”，是让它按交付标准把活干完。

---

## 先说清楚：它到底是什么

| 它不是 | 它是 |
| --- | --- |
| 一个现成的软件产品 | 六份可以直接发给 AI 的开发指令模板 |
| 一个代码库 | 一套固定工程标准的“施工说明书” |
| 一个安装包工具 | 让 AI 交付完整工程的方法 |
| 某个具体 App 的源码 | 从需求、开发、测试到发布的全流程规范 |

模板本身不写你的业务代码，也不替你编需求。它只负责一件事：**把“工程该怎么做才合格”提前定死**，让 AI 没有机会用“其余自行补全”糊弄过去。

你不需要改模板，也不需要填表。选一份，整份发给 AI，然后像聊天一样说你要做什么。

---

## 为什么“直接让 AI 写”总差一口气

| 你遇到的 | 最后变成 |
| --- | --- |
| AI 只给几个函数和伪代码 | 还得自己拼工程、补构建脚本、找依赖 |
| 需求说少了 | AI 自己决定技术栈、目录结构、异常处理 |
| 每换一个项目 | 目录分层、命名、版本写法全都不一样 |
| 交付时才发现 | 缺日志、缺配置、缺测试、缺打包说明 |
| 版本号到处抄 | 安装包、exe、文档、关于页互相打架 |
| 前端、后端、Android 一起做 | 字段、错误码、鉴权各写各的，联调靠猜 |

问题不在“AI 不会写代码”，而在于：**业务需求每次都不同，工程规范每次都要重讲。**

这套模板，就是把工程规范这一半固定下来。

## 十二层标准，把“能跑”变成“能交付”

模板不是一句“帮我写个软件”，而是一套从需求到验收的完整协议。

### 需求协议 `V0 ~ V2`

你不需要填表。用日常语言说：软件名称、核心功能、给谁用、运行环境、数据与接口、交付形态、不做什么。

AI 会先给你一段 10 行以内的“需求理解”；有会改变架构的问题，最多问 3 个；没有阻塞问题，就直接开工。

### 工程标准 `L0 ~ L11`

从技术栈、目录结构、接口与数据、日志与配置、文档、版本与版权、测试、构建、打包、部署，到验收清单和禁止事项，全部提前定好。

你拿到的不是“看起来能跑”的代码，而是一套**能构建、能测试、能打包、能部署、能验收**的工程。

## 六条技术路线

选一个最像你目标的，整份发给 AI 就能开工。

| 你想做 | 推荐路线 | 最后拿到 |
| --- | --- | --- |
| 一个原生 Windows 桌面工具 | [C++ / Qt6](docs/cpp/template.md) | Windows exe + 安装包 |
| 一个开发快、界面现代的桌面工具 | [Python / PySide6](docs/python/template.md) | Windows exe + 安装包 |
| 一个企业后端 / API 服务 | [Java 17 / Spring Boot](docs/java/template.md) | 可执行 jar + 部署说明 |
| 一个轻量 Windows 工具或常驻服务 | [Rust](docs/rust/template.md) | Windows exe + 安装包 |
| 一个安卓 App | [Kotlin / Android](docs/android/template.md) | 签名 APK |
| 一个 Web 管理后台 / 前端 | [Vue 3 / TypeScript](docs/vue/template.md) | 网站 + nginx 配置 |

**先记住三条边界：**

- MySQL 只属于 Java 后端；Android 和 Vue 都通过 API 访问数据；
- C++、Python、Rust 的 exe 不接数据库；
- Windows 桌面安装包只用 Inno Setup；Java、Android、Vue 不硬套安装器。

## 三步开始

### 1. 选一条路线

从上面六种里选一个。不确定时，先问自己：**我最后想拿到的是 exe、jar、APK，还是一个网站？**

### 2. 把整份模板发给 AI

不需要改模板，也不需要提前写需求。整份复制，直接发。建议使用支持长上下文的 AI 模型，因为一份模板就是一份完整的工程规范。

### 3. 用自然语言说需求

像聊天一样说就行：

> 做一个 Windows 桌面小工具，叫“定时关机”，能设置时间、倒计时、托盘运行，配置和日志放程序目录，最终出安装包。

AI 会先把这段话整理成需求理解，再按模板开始实现。

> 开发完成、你说“满意了 / 可以发布 / 打包最终版”之后，再读 [最终发布规范](parts/final-release-inno.md)，把工程封装成最终发布包。

## 你会拿到什么

- 一套能构建、能运行、能测试、能部署的完整工程；
- 按语言标准组织的目录，不是一堆散落文件；
- 日志、配置、异常处理、单实例、托盘等桌面软件该有的能力；
- 单元测试、集成测试、UI 测试，以及覆盖率要求；
- 构建脚本、打包脚本、发布目录、`VERSION.txt`、`SHA256SUMS.txt`；
- 三份职责分开的文档：根目录 `README.md` 是面向普通用户的广告宣传册，`docs/readme.md` 是项目说明书，`docs/develop-readme.md` 是完整开发手册；
- Windows 桌面程序最终交付 **Inno Setup 安装包**；
- 一份可以直接核对的验收清单。

## 和“直接让 AI 写”有什么不同

| | 直接让 AI 写 | 用这套模板 |
| --- | --- | --- |
| 需求 | 说少了就靠猜 | 先复述需求，再开工 |
| 工程结构 | 每次都不一样 | 按语言标准固定分层 |
| 测试 / 日志 / 打包 | 经常漏 | 列为必交付项 |
| 版本 / 版权 | 多处各写一份 | 单一真源 + 脚本同步 |
| 前后端契约 | 容易对不上 | 接口文档 + 统一错误结构 |
| 文档 | 想起来才写 | 三份文档职责固定，随交付走 |
| 验收 | 靠感觉 | 清单逐项核对 |
| 最终发布 | 给个压缩包 | Windows 用 Inno Setup，其他形态按规范交付 |

## 适合谁

- 想用 AI 做**完整项目**，不是只要一段代码；
- 需要把软件交给别人用，要求有文档、测试、构建和部署说明；
- 同时涉及后端、Android、Vue 等多个端，希望接口和结构统一；
- 希望多个项目的目录、版本、版权、文档风格保持一致；
- 不想每次换项目都重新讲一遍工程规范。

**不适合：**

- 只想要一个算法片段或示例代码；
- 完全不愿描述需求，希望 AI 从一句话猜出全部功能；
- 需要 SSR、微前端、大数据平台等模板尚未覆盖的形态；
- 希望 AI 替你决定“这次到底要做什么”。

## 常见问题

**需要我会编程吗？**

不需要你写代码，但要能说清需求、使用方、运行环境和验收标准。工程由 AI 按模板完成。

**需求要一次说完吗？**

不用。可以先说核心功能，再补细节；后续修改会覆盖先前的说法，说“其他不变”时已确认的需求继续有效。

**模板会替我写业务代码吗？**

不会。模板固定的是工程标准；业务代码由 AI 按你的需求生成。

**Java 能直接跑在 Android 上吗？**

不能。Java 模板交付的是服务端 jar；Android 客户端通过 HTTPS API 访问它。

**Android 或 Vue 能直连 MySQL 吗？**

不能。MySQL 只放在 Java 后端；Android 走 Java API，Vue 只调用 API。

**Vue 会帮我编译和打包吗？**

不会。AI 只交付源码、配置和构建说明；你执行 `npm run serve` 预览、`npm run build` 构建，再用最新版 nginx 部署。

**最终怎么变成安装包？**

Windows 桌面程序在验收通过后，按 [最终发布规范](parts/final-release-inno.md) 用 Inno Setup 生成 `*_setup.exe`、`SHA256SUMS.txt` 和 `RELEASE-NOTES.md`。默认当前用户安装，不需要管理员权限；对外发布必须代码签名。

**生成的软件可以商用吗？**

可以，生成物归使用者所有，见 [docs/license.md](docs/license.md)。但 Qt / PySide6 等第三方组件的许可义务仍需遵守。

**模板收费吗？**

模板文本采用 AGPL-3.0，见 [LICENSE](LICENSE)；你可以自由使用、修改和分发。
